Review when started directly by the owner or by an owner-authorized ticket-loop after an implementer ready comment. Each initial review/re-review is a new session that has not implemented/committed to this branch and does not inherit implementation context. Follow [AGENTS](../../../AGENTS.md) and the shared [tracker contract](../../../docs/agents/issue-tracker.md); findings come from current GitHub/repository sources, not implementer summaries.

## Workflow

1. **Pin scope.** Read the current PR/head, original Issue/comments, spec, parent Spec required behavior and applicable standards; pin head and merge-base with latest `origin/main`. Apply tracker [dispatch/isolation preflight](../../../docs/agents/issue-tracker.md#review-dispatch-shared-contract) before dispatch, including direct invocation. Create your own review worktree at that head. Derive acceptance independently; implementer summaries are navigation. For re-review also pin prior review/head and changed inputs. Done: original requirements and changed-file scope identified at a known head, with feasible independent topology or an explicit dispatch block.
2. **Inspect both axes.** Apply the risk rule below and tracker dispatch contract. Ordinary tickets use one reviewer for both axes. High-risk review uses [code-review](../code-review/SKILL.md) briefs for separate parallel Spec/Standards agents; an independent aggregator reconciles evidence, or an authorized non-implementing coordinator directly dispatches/relays the two axes. Each axis reads original sources in its own worktree. Inspect every mapped requirement on first review; on re-review apply the incremental coverage rule below. Done: both axes have findings or explicit zero findings, and required coverage has evidence or gaps; a partial launch is not dual-axis completion.
3. **Verify.** Recheck findings against diff, code, tests and documents; remove false positives. Follow [verification rules](../../../docs/agents/verification.md) for risk-based independent reproduction and SHA/command/count/environment/scope/attribution. Classify findings below. Done: each finding has requirement/standard, evidence, consequence and classification; required unverified behavior remains a gap.
4. **Publish and stop.** Post a comment beginning `**Independent reviewer:**` using the first-review or re-review format below. For direct dual-axis dispatch each agent publishes its attributed axis record; together they must cover both axes and complete required coverage. Refresh PR head/checks before publishing; a changed head makes the reviewed SHA stale under tracker rules. Never push to the PR branch. Clean your review worktree under the tracker contract and report any retention. Done: GitHub has independent findings/coverage/conclusion for the named SHA; zero findings do not turn unverified criteria into verified ones.
5. **Re-review incrementally.** A new owner/coordinator-started session reads prior review comments and compares prior reviewed head to current head. CI pending does not prevent review; publish the review conclusion and CI state separately, following tracker's three handoff states. Verify every prior blocker and each suggestion's disposition; inspect changed behavior, neighboring failure modes and affected outputs/acceptance. Cite unchanged prior coverage instead of rewriting it. Expand for omissions or newly discovered risk, upgrading topology when warranted. New blockers remain valid; classify their origin as prior omission, fix regression, interpretation change, or uncertain, citing original requirements/owner clarification for interpretation changes. Done: prior findings have evidenced dispositions, affected coverage is current, and the conclusion applies to the named latest head. Owner merge and the loop's three-cycle coordination limit do not waive blockers.

## Publication formats

**First review:** begin `**Independent reviewer:** Reviewed head: <SHA>` as the declaration index; then base SHA, risk/verification scope, separate `Spec` and `Standards` sections, full acceptance coverage under Spec, classified findings, actual verification/attributed evidence/limits and overall conclusion. Direct axis records name the axis and counterpart link when available; missing counterpart remains incomplete. Publish all verified findings from the pass together.

**Re-review:** begin the same current-head declaration index; then prior review link and before/after SHAs; prior finding dispositions with evidence; changed/affected acceptance coverage and neighboring risks; new evidence/limits; separate Spec/Standards deltas and current-head conclusion. Reference unchanged coverage in the prior record; do not require a full rewritten matrix each round. Reconstruct absent/unreliable prior coverage and report omissions instead of treating missing rows as passes. Refresh changed sources/head/checks, and read original sources for affected judgments independently of implementer explanations.

## Risk rule

High risk includes changes to execution timing, price/return semantics, accounts/costs, identity compatibility or contracts across modules. Expand independent review into parallel Spec/Standards axes for these tickets; upgrade if inspection discovers such risk. Ordinary changes, including a thin vertical slice without these contract risks, can use one reviewer. State the judgment and verification scope in handoff/review; uncertainty with concrete risk warrants escalation, not silent model downgrades. This is separate from the implementer's own acceptance self-check.

## Acceptance coverage

On first review publish `Issue/spec requirement | implementation evidence | verification/output evidence | status` for all original Issue/spec and parent Spec required behavior. On re-review publish affected rows and references to unchanged prior coverage per the format above. Derive from original requirements; the implementer mapping is navigation, not proof. Distinguish implemented, partial/missing and unverified, citing actual checks and synthetic/real-data limits.

Trace actual entry point to observable output, including input loading/invocation/writing and persisted reports where applicable. Independently select risk-relevant counterexamples: incomplete-definition bypass, first use, warmup/first/last/pending states, multi-object identity, numeric boundaries, cross-module consumers, missing/empty inputs or unsupported evidence. The implementer's scenario list is not exhaustive proof. Read existing checks before proposing automation; prefer regression tests for deterministic failures over another prose rule.

## Finding classification

- **Blocking:** evidenced failure of Issue/spec or mandatory repository standard with a concrete consequence; cite requirement and counterexample/path. Missing required verification remains an acceptance gap even when disclosed. Environment limits alone are not code defects: specify what remains unverified and whether acceptance requires it.
- **Non-blocking:** optional design/style suggestions or follow-up outside acceptance. Label judgment calls; justified deferral does not prevent completion. Do not require unrelated refactors.

Propose scope/acceptance changes for owner clarification; retain valid blockers without enlarging or weakening requirements. Reviewer conclusions remain PR comments; the coordinator relays them without rewriting them.

Assess ticket size and contract boundaries using the shared [scope rule](../../../docs/agents/ticket-scope.md), including valid legacy clauses and owner decisions. A line count or thin slice spanning layers alone is not a split finding; cite the independent contract, triggered owner-decision condition without authorization, or acceptance gap. Same-scope necessary fixes follow that rule's continuation conditions.

Environment preflight, compact read-only status, test-count records and opt-in closed-issue triage cleanup: [workflow tools](../../../docs/agents/workflow-tools.md). Apply [scope authority](../../../docs/agents/ticket-scope.md) for major-implementation 800 / estimate×2 / total 2000 review points and explicit hard budgets; tests and effective same-contract fixes continue when its conditions hold. Final-head review and test rerun scope are separate: use [impact-based evidence reuse](../../../docs/agents/verification.md#最终-head-与影响复用).
