# POC-0 综合结论

日期：2026-09-28。本文汇总票据 01–13 的实现和实测证据，供 Rust-first MVP 决策参考。结论只覆盖列出的合成输入、代码版本、机器和测量边界；不构成生产 Engine 选型、真实 ETF 业绩验证或 PIT 证明。

## 决策摘要

| 比较 | 结论 | 当前证据支持什么 | 不支持什么 |
| --- | --- | --- | --- |
| B1：Custom SoA / Arrow / Polars S2 | **defer Custom SoA** | 64 instruments × 252 sessions 下，三布局通过独立 golden、跨布局投影及冷热 cache checksum 对拍。SoA 并行 Runs/s 相对最佳替代在 miss 为 +8.99%、hit 为 +0.32%，低于预登记的 20% 门槛。 | 不证明 Polars 或 Arrow 在真实市场、其他硬件或更大规模上的普遍优势；维护成本只作定性记录。 |
| B1：Parquet / out-of-core | **adopt 已验证的受限读取能力；性能/布局选择 unresolved** | 功能验收要求在大于可用内存的数据上验证受限内存读取与分块/裁剪。本次实测样例为 10,000,029 行、256 MiB cgroup；命中 2,448 个 row group 中的 1 个、7 列中的 3 列，无 OOM；Rust 子进程 peak RSS 58,933,248 bytes。 | 10M 行/256 MiB 是本次测量条件，不是预登记性能门槛；没有预登记速度收益门槛，因此这不是吞吐量采纳结论。大部分为裁剪掉的 filler 行，不是代表性全量计算吞吐；cgroup peak 268,435,456 bytes 包含文件缓存与测量进程；单次缓存不受控数据不用于候选性能排名。 |
| B2：Fast Event / Nautilus | **`adopt`（登记的合成 S2/S3 负载）** | 3×10、3×130 判定负载及 64×252 S2/S3 稳健性负载均通过共同子集正确性门；按 2× 延迟、2× 并行吞吐和不高于 Nautilus 的 RSS 上界门槛，四个负载全部通过。使用 Nautilus 2.0.0rc5；reset parity 记录原生 `READY -> INITIALIZE` 错误，因此统一选择有证据的 `cached_conversion_new_engine`。 | 结论仅覆盖固定合成输入、本机和所测实现/依赖身份，不构成生产 Engine 选型或真实 ETF 业绩验证。比较对象是 Rust 引擎 + Rust 策略对 Nautilus + Python 策略，不是引擎核心之间的性能结论；Nautilus 以每 Run 新建引擎的回退模式运行，未选模式下的敏感性未测；四个负载中最小余量约为门槛的 4.5 倍。维护成本只记录、未评判。ADR 0012 原生停牌生命周期仍不在判定范围。范围已由项目负责人确认，见下方 B2 小节。 |
| B3：Python PyO3 callback | **reject 64×252 登记负载；其他规模 unresolved** | S2/S3 正确性通过；Python per-bar 和 batch 均未达到预登记延迟与吞吐门槛。 | 不能外推通用 Python/GIL 拐点、其他 workload 或 Python 研究平台的整体适用性。3×10 S1 callback 仅是接口正确性和微型成本样本。 |
| 构建边界 | **adopt shared lightweight path** | `--no-default-features` POC 路径复用 workspace `target/` 且依赖图排除 DuckDB；按 10 GiB 可用空间保留线记录构建成本。 | 冷构建未测；负 target 字节变化是共享缓存的变化，不是负构建成本。 |

没有候选因一次微基准而自动成为生产 Engine。POC 结果支持保留 Rust 作为账户与结果权威，并把 Python 策略入口限制在后续实测能覆盖的负载；它没有验证生产接口。

## 可追溯证据

### B1：布局、扫描与缓存

- **固定输入：**Dataset Version `poc0.synthetic.etf-daily.v1`，content SHA-256 `f5e178f3bcbf606dcc84145fd1728c2f504ba942e196eeafa08d818b48c7f132`。64 instruments × 252 sessions；S2 momentum 20/60、volatility 20，Top-N `{1,5,10}` × rebalance `{1,5}`。信号/TopK 和权重收益均通过独立期望校验，未来收益只作为评价标签。
- **源码身份：**report schema `poc0.b1.sweep.v1`；Git revision `22d9728ae19574b0ca0730a388bece86b25c2d79`；Cargo.lock SHA-256 `24b9123ee06436f427f944a2171c47187561330b96bdf096fc1502f263a5e47f`。采样时 dirty worktree 存在未跟踪文件，Git diff identity 不完整；复现以保存的源码为准。
- **登记判据：**Custom SoA 在两个 cache 状态都需比最佳替代快至少 20%；六轮候选顺序轮转、冷热条件顺序交替，单次 Run 与并行扫描分别记录。结果为 defer，不移动门槛。
- **测量：**release 并行吞吐（Runs/s）为 miss：SoA 149.63、Arrow 137.29、Polars 6.07；hit：SoA 4264.08、Arrow 4250.42、Polars 4198.37。全进程峰值 RSS 107,905,024 bytes；并非每布局独立 RSS。全部原始 Run 样本、六组扫描、checksum、硬件、依赖锁定身份与统计见 [B1 原始报告](results/b1-sweep-64x252-2026-09-27.json) 和 [RSS 记录](results/b1-sweep-64x252-2026-09-27.rss.json)。
- **语义/转换成本：**三候选都计算因子、排序/TopK、目标权重和信号日 close 到下一日 close 的评价收益；这不是含现金、费用、订单、Fill 的事件账户 NAV。SoA/Arrow/Polars 布局准备/转换计入端到端和 Run 时间，没有单独测量；SoA 第三套实现的维护负担只作定性记录，未货币化。
- **复跑：**在仓库根目录构建 `cargo build -p quant-research --no-default-features --release --locked --offline`，再运行 `target/release/quant-research benchmark-poc0-sweep --output target/poc-0/b1-sweep.json`。构建后使用 `target/release/quant-research benchmark-poc0-sweep --help` 查看可覆盖参数；缩小规模的例子见 [README sweep 章节](README.md#b1-parameter-sweep-and-factor-cache-ticket-06)。
- **工程成本：**共享 warm target dev/release 分别 5.582/9.675 秒，逻辑字节变化 -142,598,341/+53,203；cold build 和每布局独立构建成本 Unknown。构建证据见报告中的 `build_cost_evidence` 及链接记录。
- **Parquet 边界：**票据 05 要求用大于可用内存的数据验证受限内存读取及裁剪；本次样例使用 10,000,029 行输入和 256 MiB cgroup，筛选成功并跳过未命中的 row groups/columns、无 OOM；此有界读取能力通过。10M 行/256 MiB 是本次测量条件，并非预登记的性能门槛；没有登记速度收益门槛，因此 Parquet/布局的运行时性能选型仍 unresolved。受限复读 Rust 子进程 peak RSS 为 58,933,248 bytes，cgroup peak/max 均为 268,435,456 bytes，`oom=0`、`oom_kill=0`。cgroup 峰值含文件缓存及测量进程，不能当作 Rust 进程 RSS。输入 hash、完整 cgroup 计数、复跑命令及不代表全量吞吐的限制见[票据 05](../../.scratch/poc-0-benchmark/issues/05-parquet-and-out-of-core.md)。

### B2：事件账本与 Nautilus

**结论范围（项目负责人 2026-09-29 确认，Issue #25）：**在登记的四个合成日频 L1 负载、Apple M1 本机、Nautilus 2.0.0rc5（Python 策略、每 Run 新建引擎）条件下，自研 Rust Fast Event 加 Rust 策略在延迟、吞吐和内存上都大幅超过登记门槛（最小余量约 4.5×），正确性共同子集一致。据此批准 MVP-3 自研 Fast Event L1 作为高吞吐事件层。它不构成引擎核心之间的性能结论，不否定 Nautilus 作为 Accurate / Live 后端的候选地位，不对维护成本做判断，也不替代 MVP-3 自己的逐日账本、费用追溯和与 Vector 对拍的验收。

下列条目按时间保留证据链；标注“历史快照”的条目是当时的状态，已被 Issue #3 的正式结论取代。

- **共同 correctness 子集：**S1 的手算 3 ETF × 10 日金标准含 `UNKNOWN`/`HALTED`、缺 bar、非零佣金/滑点；S2 复用固定目标和状态 fixture，S3 使用版本化 3 instrument × 130 weekday MA20/60 fixture。共同字段逐项对拍通过；T 日收盘形成信号、下一可用日 open 执行。S2/S3 参数、费用（初始资金 100,000 CNY、100 股手、每侧 10 bps 滑点、100 CNY 最低佣金）和逐日预期见 [票据 09](../../.scratch/poc-0-benchmark/issues/09-b2-strategy-parity-and-throughput.md)。
- **Nautilus reset mode（2026-09-28，票据 #2）：**固定版本 `2.0.0rc5` 下，对 S2/S3 判定 fixture 与两套 64×252 robustness fixture，worker 每次只准备一次 venue/instrument/data；新建引擎参考与 setup 后连续三次 `reset()` Run 的 projection checksum、现金、订单/持仓计数、开放订单/持仓、迭代数、回放边界、strategy/instrument cache 及每 instrument quote cache 全部一致。判定 S2/S3 checksum 分别为 `5ec4f580565a9bdb3d703e4ebdf4171fba10a14e93f092d2c9fd50ed61711203` / `ee74058226f1f2c744db19c74943300ffe476027d1caa802e79f755791389cc3`，均与之前通过 Rust golden 字段对拍的 Nautilus 投影 checksum 一致；稳健性 S2/S3 reset checksum 分别为 `e43fb494718e7765850e7ac0f29cf93e0e98c2fb48b5a6316792e3fd83bf04cf` / `4bbfd275fda6db683bf5a93b1bcc8e3b9f77e37fd0814cd763edca733341de4f`。但所有 reset Run 都打印 `Error initializing trader: Invalid state trigger READY -> INITIALIZE`；报告以 `engine_log.error` 标出首个差异并统一回退至 `cached_conversion_new_engine`，不因 checksum 相等而忽略引擎错误。版本、revision、dataset hash、错误日志和 state snapshots 见 [reset parity evidence](results/b2-nautilus-reset-parity-2026-09-28.json)，golden 来源见 [checksum manifest](fixtures/b2-nautilus-reset-golden-checksums-v1.json)。按选定 fallback 模式重跑后，S2/S3 两个 decision load 均为 registered `adopt`；当时 64×252 registered robustness 尚未复核，完整 B2 结论由下方 Issue #3 完成。
- **Registered 64×252 robustness 与 B2 formal conclusion（Issue #3，2026-09-28）：**将票据 07 reset-mode evidence 传入修复后的 correctness-first coordinator，先校验四负载证据与 ADR 0013 选定模式，再对两套压力 fixture 各做两次 Nautilus/Rust 投影对拍；S2/S3 均通过。reset 每次运行产生原生 `READY -> INITIALIZE` 错误日志，所以 20 次串行样本和五组交替双 worker 样本均使用同一 fallback `cached_conversion_new_engine`。S2 Fast Event/Nautilus 串行中位数为 11,285,375 / 153,936,604.5 ns，并行中位 106.91 / 11.85 Runs/s，RSS 为 88,670,208 / 298,598,400 bytes；S3 分别为 2,514,584 / 53,429,875 ns、515.61 / 33.24 Runs/s、86,278,144 / 243,712,000 bytes。Nautilus RSS 是两 worker 峰值之和上界。两种压力负载均满足已登记门槛，S2/S3 小负载 registered decision loads 也均通过；最终 B2 结论为 `adopt`，先验关于两种策略速度门槛和 Rust RSS 较低的预测成立。跨登记负载规模（3×10/3×130 与 64×252）结论均为 `adopt`，没有观察到结论翻转；其他时间边界和未选 Nautilus 模式的敏感性仍 unresolved，因为 reset 产生原生引擎错误且没有有效替代口径样本。选择 fallback 的原因是 Nautilus 原生 reset 错误日志，而不是性能未达标。完整每 Run 样本、correctness diagnostics、敏感性说明、环境与源码身份见 [formal robustness report](results/b2-formal-robustness-reset-selected-2026-09-28.json)，release build 与 10 GiB gate 见 [build record](results/b2-formal-release-build-2026-09-28.json)。
