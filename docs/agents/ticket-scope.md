# 票据范围与 Prepare

`to-tickets` 起草近期票、`implement-ticket` Prepare、`ticket-loop` 协调及独立 review 共用本规则。目标是提前识别独立契约，让 Prepare 只复核增量；验收要求仍以当前 Issue/spec 及负责人裁决为准。

## 先判契约，再看规模

一票交付一项可独立验收的行为或契约。独立契约有自己的输入、结果及失败语义，能单独验收，并有独立使用者或交付价值。同一行为的页面、HTTP、CLI、存储适配可以属于一个薄纵向切片；接口数量、文件数量和跨层本身不构成拆票理由。

共享浏览器框架等基础能力可以独立成票：明确使用者、复用边界及可运行的验收路径，无需为每票增加新 UI。产品票仍须覆盖自己承诺的生产闭环；基础能力完成不表示产品验收完成。

约 800 changed lines 是范围复核触发点。低于它仍要识别多个独立契约；略超它且边界单一、增量主要来自必要测试时，可申请一次预算例外。按契约边界拆分，不按文件、技术层或凑行数拆分，也不靠删测试、压缩代码或延后必要验证达标。

规模统一用新增行 + 删除行，分列生产代码、手写测试（含手写 fixture/验证脚本）、文档、生成文件，并给合计区间。生成文件注明来源；单独列出便于判断工作量，仍计入总量。估算区间上沿超过约 800 行即触发复核，避免以乐观下沿代替预算。

## 近期票的范围检查

`to-tickets` 为当前无 blocker 或紧接当前前置、计划近期实施的票做简短检查，记录所依据的代码基线及相关入口/测试证据，使用下方六项。能引用当前上下文的证据就复用；检查到足以判断缺口、验收路径和估算区间即可。

远期票保留行为、边界和依赖，标记范围检查待补；临近实施时补齐，不提前做深度设计。尚待补齐、口径未定或预算待授权的票用 `needs-triage`；检查完成且口径明确后才能标 `ready-for-agent`，实际认领仍须无 blocker。

## Prepare 六项

Prepare 对照 Issue 中的范围检查与当前基线，只刷新已变化的入口、前置能力、验收或估算；已有结论可引用。不重新设计整票；旧票缺少范围检查时补一次。

```text
交付：一个可观察行为（或基础能力的使用者与可验收结果）
现状：已有生产入口、实际缺口及代码/测试证据；注明基线与本次变化
边界：几个独立契约，分别是什么；同一行为的跨层适配说明关系
验证：生产入口 → 持久结果 → 可观察输出，列必要正常/失败/边界场景
规模：生产代码 / 手写测试 / 文档 / 生成文件各自区间、合计与估算依据
结论：继续 / 申请一次预算例外 / 按明确边界拆分，并给理由或授权引用
```

不适用持久化的只读或基础能力票，在验证项注明原因和对应可观察产物，不额外制造存储要求。接口、schema 或量化口径变动所需的契约文档及必要 ADR 也计入估算。

## 决策与授权

- **继续：**一个行为/契约，验收路径明确，估算不触发规模复核，或已获授权且仍在批准范围和预算内。将六项结论留在 Issue，进入实现。
- **申请一次预算例外：**触发规模复核但边界单一时，先说明保持单票的理由、四类估算、合计上限、必要测试及验证风险，请负责人在本 Issue 明确授权。批准须固定交付范围与总行数预算；开工前完成，已有授权在范围和预算内直接复用。
- **按明确边界拆分：**包含多个独立契约，或无法给出可控单票预算时，提出子票各自行为/契约、估算及依赖，并将原验收逐项映射到子票；等负责人确认后调整票据。拆分后的近期票同样完成范围检查，不能仅留下“超过 800 再拆”。

待授权或待确认拆分时，已认领票改为 `needs-triage`、移除自己的 assignment，保留结论并按 [tracker](issue-tracker.md) 处理工作区。获批后恢复 `ready-for-agent`，重新核对资格再认领。预算例外不豁免验收、必需验证或独立 review。

实施中出现新的独立契约、须扩大范围才能补齐的验收缺口或预计超出已批准预算，暂停受影响工作，在本 Issue 只复核新增事实并申请决定；范围和预算内的实现、修复及估算波动继续，不重复申请。首次发现超规模时也走此流程，并说明前置检查漏项。

旧票的范围检查在下次 Prepare 增量补齐；票内仍有明确“超 800 必须拆”等特殊要求时，在该 Issue 引用本规则提出调整并等负责人裁决，不能静默覆盖票内要求。保留原验收和历史结论，既有拆分不因规则更新自动撤销。
