# POC-0：可复跑的性能与一致性基准

Status: ready-for-agent
Type: spec

## Problem Statement

项目已确定 Rust-first、多市场研究与三级 Engine 的目标，但三项关键实现选择仍缺同条件证据：Vector 热路径应使用 Polars、Arrow 还是 Custom SoA；自研 Fast Event 在相同交易语义下相对 NautilusTrader 是否有足够收益；Python 逐 bar 回调在什么规模成为瓶颈。现有 ETF 回测和 B1 标量读取 smoke 不能回答这些问题。若直接按单次耗时或不同语义的收益率选择架构，后续会承担错误的性能、维护和量化正确性成本。

## Solution

提供一个可复跑的 POC-0 benchmark 入口。研究者指定不可变 Dataset Version、参考 Strategy、参数、成本、Engine 候选和测量规模后，入口先对独立金标准和共同语义进行正确性检查，再输出原始耗时、资源使用、结果 checksum、环境与代码/数据身份、不可消除的语义差异和每项 `adopt / defer / reject / unresolved` 建议。B1、B2、B3 共用输入与报告契约，在候选实现内部保留各自数据布局与运行方式。

先完成 B1 的完整工作负载，再接入 B2 与 B3。POC 的结论只覆盖测量过的负载、版本和硬件；未取得可比结果时保留 `unresolved`。真实 ETF 历史业绩的 PIT、分红和执行状态门槛继续单独验收。

## User Stories

1. 作为量化研究者，我希望用一条命令重跑 POC-0 的任一比较，以便复核技术结论。
2. 作为量化研究者，我希望每次 Run 指向固定的 Dataset Version 和内容 hash，以便数据修订后仍能重现旧测量。
3. 作为量化研究者，我希望能看到合成数据的 seed、交易日历、Instrument 数量、bar 数和缺失规则，以便理解工作负载。
4. 作为量化研究者，我希望先用独立手算的 3 ETF × 10 日金标准检查结果，以便性能数字建立在正确行为上。
5. 作为量化研究者，我希望金标准包含缺 bar、不可成交状态和非零交易成本，以便覆盖日频执行的关键边界。
6. 作为量化研究者，我希望所有参考 Strategy 的 T 收盘信号都在下一可用 open 执行，以便避免未来函数。
7. 作为量化研究者，我希望未来收益只作为评价标签，以便它不污染 Strategy 决策。
8. 作为量化研究者，我希望 B1 在相同的日频面板上比较动量、波动率、排名、TopK、目标权重和简化组合收益，以便测量真正的研究热路径。
9. 作为量化研究者，我希望 B1 明确 null、NaN、缺日、窗口边界和平局排序，以便三种布局产生相同信号。
10. 作为量化研究者，我希望 B1 分开报告 Parquet 扫描、列裁剪、格式转换和内存计算，以便知道优化收益发生在哪里。
11. 作为量化研究者，我希望 B1 测量因子缓存命中与参数扫描复用，以便评估大规模 Experiment 的实际吞吐。
12. 作为量化研究者，我希望 B1 验证大于内存的数据能分块处理，以便平台不依赖整库装入 RAM。
13. 作为 Engine 开发者，我希望用 S1 Buy & Hold、S2 Momentum Rotation 和 S3 MA20/60 作为共同参考 Strategy，以便覆盖简单持有、截面轮动与状态型信号。
14. 作为 Engine 开发者，我希望 S2 固定窗口、方向、TopK、调仓日和权重规则，以便不同 Engine 的结果可比。
15. 作为 Engine 开发者，我希望 B2 先比较单 Venue、长仓、市价单、L1 成交和固定成本的共同子集，以便剔除复杂撮合语义的干扰。
16. 作为 Engine 开发者，我希望 B2 对逐笔 Fill、现金、持仓、成本和每日权益做对拍，以便定位交易语义差异。
17. 作为 Engine 开发者，我希望 B2 单独记录 Nautilus Adapter 的转换和初始化时间，以便判断 Backend 接入的真实代价。
18. 作为 Engine 开发者，我希望无法对齐的撮合或时序规则在报告中逐项说明，以便不把模型差异误判为 Engine Bug。
19. 作为 Strategy 开发者，我希望 B3 用相同事件流和决策逻辑比较 Rust Native 与 PyO3 Python 回调，以便估计逐 bar 接口的成本。
20. 作为 Strategy 开发者，我希望 B3 包含空回调、真实策略回调和批处理候选，以便区分跨语言固定开销与策略计算。
21. 作为 Strategy 开发者，我希望 B3 测单 Run 与多个独立 Run 的吞吐，以便识别 GIL 和并行扩展边界。
22. 作为 Strategy 开发者，我希望 Python 回调版与 Rust 版先通过相同的信号和 PortfolioResult 对拍，以便吞吐差异不掩盖行为差异。
23. 作为 Experiment 维护者，我希望数据生成、读取、转换、因子、回测和序列化分别计时，以便识别端到端瓶颈。
24. 作为 Experiment 维护者，我希望冷热缓存、单 Run 延迟和并行 Runs/s 分开报告，以便不混淆不同使用场景。
25. 作为 Experiment 维护者，我希望固定预热、重复次数、线程数与输入规模，并保存每次原始样本，以便统计量可复核。
26. 作为 Experiment 维护者，我希望同时看到中位数、p95、吞吐和峰值 RSS，以便速度与内存成本一起进入决策。
27. 作为 Experiment 维护者，我希望记录 CPU、内存、操作系统、编译参数及依赖锁定版本，以便比较同条件测量。
28. 作为 Experiment 维护者，我希望脏工作树附差异摘要或标为不可完全复现，以便不会把临时构建误当正式基准。
29. 作为项目负责人，我希望任何候选在正确性检查失败时停止性能比较，以便不会选出快速但错误的实现。
30. 作为项目负责人，我希望在测量前登记目标负载与有意义的收益门槛，以便结果出来后不移动判定标准。
31. 作为项目负责人，我希望每项比较给出收益、资源、转换成本、语义风险和维护成本，以便选择能长期承担的方案。
32. 作为项目负责人，我希望某项依赖安装失败或语义无法对齐时仍得到 `unresolved` 和复跑说明，以便 POC 如实交接。
33. 作为审阅者，我希望报告区分已实现、已通过合成检查、已测性能与真实数据验证，以便不把 POC 结果当成生产能力。
34. 作为审阅者，我希望能从汇总结论追溯到原始测量、固定输入和版本身份，以便独立检查推荐理由。
35. 作为 POC 开发者，我希望在新增重依赖前看见构建依赖图、增量编译耗时、release 构建耗时和产物增量，以便控制迭代成本与磁盘使用。
36. 作为 POC 开发者，我希望 B1/B2/B3 共用可复用的构建缓存且计算候选的轻量开发路径不编译 bundled DuckDB，以便避免重复占用磁盘。
37. 作为项目负责人，我希望可用空间不足时停止新增构建、保留失败证据并让不受影响的候选继续推进，以便资源限制不伪装为性能结论。

## Implementation Decisions

- 以**一个可复跑 benchmark CLI 的输入与输出**作为主验收接缝。入口负责固定数据与配置、调用候选实现、检查正确性并生成报告；各候选 Engine 和布局不为测试而共享内部对象。现有 B1 CLI 可作为起点，扩展到共同契约。
- POC 使用一个版本化合成 Dataset 与独立期望结果；再用许可明确的已发布 ETF 快照复核数据形状。合成输入包括交易日历、OHLCV、可用时刻、缺失/状态和来源身份。真实快照不能替代 PIT 或投资业绩验收。
- S1、S2、S3 是固定参考 Strategy；S2 为主要贯穿样例。日频对拍沿用当前已确认的 T 收盘形成信号、下一可用日 open 执行。Vector 的简化权重收益与事件账本分别声明假设，仅在共同语义子集上比较。
- B1 同时包含 Polars 表达式路径、Arrow 列批次路径和 Custom SoA 路径；标量逐值读取只保留为诊断切片。扫描/解码、转换、计算、缓存复用和端到端分别测量。Custom SoA 的采用取决于代表性负载的净收益与维护成本。
- B2 用最小 Fast Event 原型与固定版本的 Nautilus Backend/Adapter 比较。平台 Domain 的 Instrument、Order、Fill、账户与 PortfolioResult 语义由本项目控制；候选 Backend 的类型和生命周期停留在 Adapter 内。当前 ETF 回测可作工程基线，但不称为完整 Fast Event Engine。
- B3 使用同一事件驱动器比较 Rust Native Strategy 与 PyO3 Python `on_bar()`；空回调、实际策略和可批处理变体分别测量。Python 策略输出仍由 Rust 的账户与绩效逻辑解释。
- 原始结果保存输入 hash、有效配置、Strategy/Engine/依赖版本、代码修订或差异摘要、seed、成本、环境、重复样本、checksum、资源和语义差异。汇总报告注明哪些明细未保存；省略不等于零。完整 `ResultLevel` 产品契约属于后续 MVP。
- 运行器对无法安装、超出资源预算或语义不匹配的候选保留错误与 `unresolved` 状态，不填造耗时或收益。任何架构选择须在完整测量后形成单独结论，POC 不自动改写现有量化核心。
- 新增 [票据 13：构建资源与轻量边界](issues/13-build-resource-boundary.md) 作为后续资源密集任务的前置条件。先清点现有 target/依赖图与磁盘余量，再在独立 crate 或可选 feature 间以实测选择；轻量 POC 路径须避免编译 bundled DuckDB，并让候选复用同一构建缓存。03/04 已开展工作保持原状态，追补构建记录缺口，不因新票重做实现。
- 会新增构建产物的任务开工前确认至少 10 GiB 可用空间，并估算完成后仍有至少 10 GiB；不满足时停止该构建，保存命令、空间快照、错误/估算依据与复跑条件，候选标 `unresolved`，继续不受影响的工作。先归因再处理产物；不得由票据自动清空整个 target 或删除正在使用的构建缓存。
- 编译耗时与构建产物增量是单列工程成本，不与运行时吞吐合成单一分数。记录已有缓存下的增量构建和正式 release 构建；冷构建只在资源足够时做。运行时比较仍须使用同一 release profile、依赖版本、输入和线程条件，先过正确性门槛。固定编译秒数门槛待基线测量后再定。

## Testing Decisions

- 测试只断言从固定输入和配置到 CLI 报告的**外部行为**：可重放身份、共同策略输出、账本与成本、错误状态、原始测量记录和结论边界。不用候选内部容器类型、调用次数或私有函数形状作验收。
- 主金标准是独立给定的 3 ETF × 10 交易日输入与逐日预期；覆盖 T close → 下一 open、缺 bar、不可成交、末日待执行目标、佣金/滑点以及 `NAV ≈ cash + Σ(quantity × 当日估值价)`。离散事件与数量精确相等；浮点容差事前登记。现有 ETF Rotation 的独立手算账本测试和状态门槛测试可作先例，但期望值不能由被测 Engine 生成。
- B1 从同一输入验证窗口端点、缺失传播、排序平局、TopK、权重、组合收益与 checksum；参数扫描和缓存命中不得改变结果。B1 的大样本还要确认列/日期裁剪和分块处理实际生效。
- B2 对相同事件序列逐日比较 Order/Fill、现金、持仓、成本、估值与 PortfolioResult；不能对齐的 Backend 语义单独报告，不强制数值相等。现有回测对缺旧仓 open 的整次延期和状态 fail-closed 行为是相关先例。
- B3 对同一事件流比较 Rust/Python 的决策及最终报告；空回调用于估计固定跨语言成本。线程数与进程数是输入条件，吞吐比较须说明 GIL 与并行方式。
- 性能测试在 release 构建上进行，先通过正确性再计时；记录预热、每次重复、冷/热缓存、转换与序列化、峰值内存、机器/编译环境。不得把一次 smoke 或固定候选顺序的数字用于最终胜负判定，也不以机器相关的绝对耗时作为常规单元测试断言。
- 构建资源门槛按统一协议记录空间前后值、target 目录增量、构建 wall time、依赖/feature/profile、缓存冷热状态和失败原因。不得为了测冷构建而清空整个 target；空间不足可以交付可复跑条件和 `unresolved`，不能虚报测量。
- 完成判据：B1/B2/B3 各有可复跑命令、固定输入与独立期望、原始测量、语义差异、资源/吞吐汇总和有依据的状态结论。某候选确实不可运行时，仍须交付失败证据和 `unresolved`，不能宣称该项已比较完成。

## Out of Scope

- 正式实现完整 Vector、Fast Event、Accurate 或 Live Runtime；POC 只实现比较所需的最小可运行子集。
- 生产级 Nautilus 接入、Broker/Gateway、真实下单、跨 Venue 账户结算与风控。
- A 股、美国市场、CEX 或 DEX 的完整行情接入；AMM/MEV、L2/L3/L4 撮合、延迟/排队/部分成交的全面模拟。
- 完整 Strategy DSL、分布式调度、GPU、Kubernetes、微服务、Web 页面。
- 用历史 ETF 收益数字证明无偏策略表现，或以合成 POC 关闭历史 Universe、公司行动、交易状态的 P0 风险。
- 仅凭标量访问 smoke 决定 Custom SoA，或仅凭不同 Engine 的 Sharpe 差判断实现 Bug。

## Further Notes

- 当前独立 B1 smoke 只覆盖标量访问；主 benchmark 的 SoA、Arrow、Polars S2 候选已验收，但 Arrow release 性能样本、Parquet/out-of-core、代表性规模与资源比较未完成。B2 有最小 Fast Event S1 原型，B3 未启动。已有 smoke 和候选验收均不构成架构选型。
- 目标架构与既有决策见 `ARCHITECTURE.md`、ADR 0009–0011；详细测量协议见 `docs/poc-0-benchmark-spec.md`。本 spec 负责工作范围与验收；技术协议变更时须同步两处。
- 本地 issue tracker 以本文件的 `Status: ready-for-agent` 表示已可由 Agent 接手；现有实现票据为 01–12，构建资源前置票据为 13。已开展票据的状态以各自文件为准。
